Design choices

  • 12 endpoints; Swagger at /docs
  • Schema owned by Alembic migration 0001, with CHECK constraints (amount > 0, valid type)
  • Migrations run once (Compose one-shot service / K8s initContainer), not in every API process
  • Names normalised in the Pydantic schema, so every path stores "Ramesh"
  • Config only from env: ConfigMap + Secret

Troubleshooting

Two real incidents, two lessons

1 · Postgres CrashLoopBackOff

8 GB node at 419 % CPU; pg_isready with a 1 s liveness timeout timed out → kubelet kept killing a healthy database → every API Pod 0/1.

Fix: patient DB liveness (30 s delay, 5 s timeout, 6 failures), configurable probe timeouts, API boots without DB, HPA max 3.

Lesson: liveness restarts; readiness only removes from the Service.

2 · exec format error

GitOps rollout to the Apple Silicon node crash-looped: images were linux/amd64, node is arm64.

Fix: build each tier on native amd64 + arm64 runners, scan all 4, publish one multi-arch tag per SHA.

Lesson: the rolling update protected users — new Pods never got Ready, old ones kept serving.

Wrap-up

What I'd do next in production

  • Amazon RDS instead of Postgres in the cluster (backups, failover)
  • CI writes the promotion commit itself (Argo CD Image Updater)
  • Sealed Secrets / External Secrets for the API key
  • cert-manager TLS on the Ingress
  • Remote Terraform state (S3 + DynamoDB lock)
  • Alertmanager → Slack/WhatsApp
  • Load test in CI with SLO checks (p95 < 300 ms)
  • Voice input for shopkeepers (Hindi + English)
